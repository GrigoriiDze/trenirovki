# План 02 — Бэкенд: Supabase + синхронизация

**Создан:** 2026-09-03. Решение Григория: бэкенд раньше ядра тренировок — фундамент под систему здоровья (документы, мультиустройство, агенты).

## Цель

Источник истины — Supabase (Postgres + Storage + Auth). Приложение **остаётся офлайн-first для зала**: Dexie — локальный слой (мгновенные чтения/записи, работает в подвале), Supabase — синхронизация и бэкап. Один пользователь — Григорий, вход по magic link.

## Архитектура

- **Dexie не выбрасываем.** Он становится локальной половиной local-first: UI всегда читает и пишет в Dexie, синк едет фоном.
- **Слой синхронизации:** pull при загрузке и реконнекте, push-очередь на каждую локальную запись.
- Один пользователь → **last-write-wins**, разрешение конфликтов не нужно.
- Тренировка — естественная транзакция: пишется локально по подходу, уезжает когда есть сеть.
- Storage — под будущий модуль документов (план 03).
- RLS: каждая строка по `user_id = auth.uid()`.

## Что уже есть

Схема из плана 01 (`src/db/schema.ts`): `exercises`, `programVersions`, `programSlots`, `sessions`, `setLogs`. Её зеркалим в Postgres, добавляя `user_id` и `updated_at`.

## Этап 0 — Проект Supabase → **на Григории**

- [ ] 0.1 Создать проект на supabase.com, регион **EU (Frankfurt)** — ближе РФ, чем US
- [ ] 0.2 Скопировать **Project URL** и **anon/public key** (Settings → API) → прислать сюда. Пойдут в Vercel env и локальный `.env`
- [ ] 0.3 Authentication → Providers → **Email** включить, magic link. Для своей почты выключить «Confirm email»
- [ ] 0.4 Прислать **service_role key** (или прогнать сид-скрипт самому по инструкции) — разово для заливки программы

## Этап 1 — Схема БД

- [ ] 1.1 `supabase/migrations/0001_init.sql`: пять таблиц-зеркал Dexie + `user_id uuid`, `updated_at timestamptz`, `deleted boolean` (мягкое удаление для синка)
- [ ] 1.2 RLS: `sessions`, `set_logs` — только свои; `exercises`, `program_*` — читают все залогиненные, пишет только владелец
- [ ] 1.3 Триггер `updated_at = now()` на каждый UPDATE
- [ ] 1.4 Прогнать миграцию в проекте (SQL Editor или CLI), засеять программу v1 (скрипт под service key)

## Этап 2 — Клиент и вход

- [ ] 2.1 `@supabase/supabase-js`, клиент-синглтон из `import.meta.env`
- [ ] 2.2 `src/screens/auth.tsx`: одно поле email → «прислать ссылку» → возврат по ссылке уже залогинен
- [ ] 2.3 В `App`: нет сессии → только экран входа; есть → приложение
- [ ] 2.4 «Выйти» — маленьким пунктом (пока в плитке «Программа» или в шапке хаба)

## Этап 3 — Синхронизация

- [ ] 3.1 Push: обёртка над записями в Dexie кладёт операцию в таблицу `_outbox`, воркер флашит в Supabase при сети
- [ ] 3.2 Pull: при старте и `online` — тянуть строки с `updated_at > последней синхры`, мёржить в Dexie (server wins)
- [ ] 3.3 Индикатор: «синхронизировано» / «N ждут сети» / «оффлайн» — маленькой строкой на хабе
- [ ] 3.4 Первый вход на новом устройстве — полная загрузка всех таблиц пользователя
- [ ] 3.5 Кнопка «выгрузить JSON» остаётся — холодный бэкап на случай, если что-то пойдёт не так с синком

## Этап 4 — Проверка

- [ ] 4.1 Самолётный режим: залогинен, провёл тренировку (когда будет экран из плана 01), вернул сеть → данные в Supabase
- [ ] 4.2 Второй браузер / инкогнито: залогинился → данные подтянулись
- [ ] 4.3 `npm run shot`: экран входа, индикатор синка
- [ ] ⛔ 4.4 **Гейт:** Григорий логинится на телефоне, ставит PWA заново, данные на месте

## Риски

- **Supabase из РФ** — API на AWS, обычно доступен, но бывали перебои. Приложение local-first, поэтому перебой синка не ломает зал: пишется в Dexie, уедет позже.
- Magic link требует рабочей почты в зале при первом входе — вход делается один раз дома, дальше сессия живёт.
